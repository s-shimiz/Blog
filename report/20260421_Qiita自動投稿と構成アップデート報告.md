# 作業報告書: Qiita への自動投稿の仕組み作成と構成のアップデート

**作業日**: 2026年4月21日

## 概要

Qiita CLI を導入し、ローカルの Markdown ファイルから Qiita への投稿・更新を自動化する仕組みを構築した。併せて、リポジトリ全体の構成を Qiita 統一に変更した。

## 1. Qiita CLI の導入

### インストール

- `@qiita/qiita-cli` を devDependencies にインストール
- `npx qiita init` で初期設定ファイルを生成
- `npx qiita login` で Qiita API トークンを使って認証

### 主要コマンド

| コマンド | 用途 |
|---|---|
| `npx qiita preview` | ブラウザでプレビュー |
| `npx qiita new <basename>` | 新規記事の作成 |
| `npx qiita publish <basename>` | 指定記事を投稿・更新 |
| `npx qiita publish --all` | 全記事を投稿・更新 |
| `npx qiita pull` | Qiita から記事を同期 |

### 追加されたファイル

| ファイル | 説明 |
|---|---|
| `package.json` | Node.js プロジェクト設定 |
| `package-lock.json` | 依存関係のロックファイル |
| `qiita.config.json` | Qiita CLI の設定ファイル |

## 2. GitHub Actions による自動投稿

### ワークフロー

`.github/workflows/publish.yml` を作成。`main` ブランチへの push 時に `public/` 配下に変更があれば、自動的に Qiita へ記事を投稿・更新する。

```yaml
on:
  push:
    branches:
      - main
    paths:
      - "public/**"
  workflow_dispatch:
```

### 必要な設定

- GitHub リポジトリの Settings → Secrets and variables → Actions で `QIITA_TOKEN` を登録済み

## 6. drafts/ フォルダの導入

### 背景

`public/` フォルダに記事を置くと、push 時に GitHub Actions が自動で Qiita に投稿してしまうため、下書き・執筆中の記事には不向きだった。

### 対応

| フォルダ | 用途 | 自動投稿 |
|---|---|---|
| `public/` | 投稿済み記事のみ配置 | ✅ push 時に自動投稿 |
| `drafts/` | 下書き・執筆中の記事 | ❌ 対象外 |

- `drafts/` フォルダを新規作成
- 未投稿の 4 記事を `public/` → `drafts/` に移動
- `copilot-instructions.md` と `blog-writer SKILL.md` に `drafts/` の運用ルールを追記

### 運用フロー

1. 新規記事は `drafts/yyyymmdd_slug.md` で作成・執筆
2. 投稿準備ができたら `public/` に移動
3. push すると GitHub Actions が自動で Qiita に投稿

## 7. Qiita CLI のファイル名管理

### 背景

Qiita CLI で投稿すると、記事 ID（`ec68cbc4889ec28b39a8.md`）がファイル名になるため、どの記事か判別しづらい問題があった。また、元の命名規則ファイル（`20260421_flow-input-parameter-types.md`）と重複が発生した。

### 対応

- 重複ファイルを削除し、Qiita CLI 管理ファイルに統一
- ID ファイル名を分かりやすい名前（`20260421_flow-input-parameter-types.md`）にリネーム
- Qiita CLI はフロントマターの `id` フィールドで記事を識別するため、ファイル名変更は投稿・更新に影響しない
