01 / The big picture

まずは、記事が届くまでの全体像

基本は「下書き → 確認 → 公開準備」。最後の投稿処理を GitHub Actions が担当します。

  1. STEP 01

    調べる

    テーマや公式情報を確認。必要なら製品を実際に検証します。

    人 ＋ 必要に応じて AI
  2. STEP 02

    下書きを書く

    drafts/ に Markdown 形式で記事を作ります。

    人 ＋ 執筆支援
  3. STEP 03

    確認・修正する

    内容や文体をレビューし、指摘を確認して修正します。

    人 ＋ レビュー支援
  4. STEP 04

    公開を準備する

    画像や公開範囲を確認し、原稿を public/ に移します。

    人の操作
  5. STEP 05

    投稿・更新する

    main への push などをきっかけに Qiita へ反映します。

    条件を満たすと自動
ここがポイントAI 向けのエージェントや手順書は作業を支援するための定義です。記事投稿を実行する GitHub Actions とは別の仕組みです。

02 / Writing & review

人と AI で、原稿を整える

原稿は Markdown で管理します。AI に執筆やレビューを頼めますが、確認や公開の判断は人が行う流れです。

01

情報を集める

テーマを決め、公式ドキュメントなどを確認します。操作手順を紹介する場合は、画面のスクリーンショットも用意します。

02

drafts/ で下書き

yyyymmdd_slug.md の形式で保存します。執筆用のスキルには、文体や構成のガイドがあります。

執筆スキルを見る

03

レビューして直す

レビュー役は技術的な正確性・文体・構成などを確認し、指摘を返します。レビュー役自身は記事を編集しません。

レビュー役の定義を見る

04

public/ に移して最終確認

タイトル、タグ、公開範囲、画像やリンクを確認します。画像は、Qiita の読者からも参照できるか確認します。

公開前チェックを見る

Article metadata

記事の先頭にある設定

冒頭の フロントマター に、タイトルやタグ、公開範囲などを記入します。

---
title: "記事のタイトル"
tags:
  - CopilotStudio
private: true
---
  • title：記事のタイトル
  • tags：記事に関連するタグ
  • private：Qiita での公開範囲
  • id：既存記事の識別に使う管理情報
「下書き」と「限定公開」は別です。
private: true は限定公開として投稿され得る設定で、未投稿を保証するものではありません。drafts/ も、この自動投稿の対象外という置き場所であり、Qiita 上に記事が存在しないことまでは保証しません。

03 / Publishing

どのタイミングで自動投稿される？

設定されているのは、GitHub 上で動くワークフローです。ローカルでファイルを保存しただけでは起動しません。

きっかけ

main に push

public/** の変更を含む push が対象です。またはGitHub Actions 画面から手動実行できます。

GitHub Actions

投稿アクションを実行

Qiita CLI の publish アクションを呼び出します。

投稿先

Qiita に反映

対象の記事を投稿・更新します。実際の成否は実行結果で確認します。

対象外の例：drafts/ だけを変更した push では、このワークフローは起動しません。手動実行は別です。

必要な設定：GitHub のシークレット QIITA_TOKEN。現在の登録状況や投稿結果は、このフォルダだけでは確認できません。

自動投稿の設定ファイルを見る

Local preview

投稿前に見た目を確認したいとき

リポジトリのルートで依存パッケージを用意し、Qiita CLI のプレビューを起動します。public/ にある原稿の確認に使います。

設定上のアクセス先は localhost:8888。ロックファイルに記載された CLI の要件は Node.js 20 以上です。

プレビュー設定 · 依存関係

npm ci
npx qiita preview

04 / AI support

AI に頼めることと、検証の流れ

.github/ には役割・手順・定型の依頼文が置かれています。必要に応じて Copilot が参照するためのものです。

WRITER / 執筆

記事を書く

blog-writer が文体やテンプレートに沿った下書き作成を支援します。

エージェントの定義 · 詳しい手順

REVIEWER / 確認

記事をレビューする

blog-reviewer が改善点を指摘。記事ファイルの編集は行いません。

エージェントの定義 · 詳しい手順

VERIFIER / 検証

動きを試す

copilot-studio-verifier がテストやスクリーンショット取得を支援します。

エージェントの定義 · 詳しい手順

必要なときだけ

Copilot Studio を検証する場合

記事作成とは別に、検証対象を決めてシナリオを承認したうえで、ブラウザ操作・記録を行う手順が用意されています。

  1. 検証の依頼
  2. シナリオ作成・承認
  3. ブラウザでテスト
  4. 画像・結果を記録
  5. 必要なら記事化
この手順は Playwright MCP とサインイン済みの環境を前提とします。設定は .vscode/mcp.json（Edge・Playwright 専用プロファイル）にあります。初回は開いたブラウザで手動サインインしてください。

検証の依頼文 · 検証結果から記事を作る依頼文 · MCP の設定

自動化

毎週のネタ出しから投稿まで（GitHub のコメントで進める）

月曜朝に AI がネタ候補を Issue にします（/ideas テーマ とコメントすれば、いつでもテーマを指定して出せます）。自分のアイデアは /add-idea タイトル で候補に追加できます。あとはコメントのコマンドで下書き・レビュー・修正・公開準備を進めます。スクリーンショットはローカルで撮影し、ms-tech-validation の mask.py で機密情報を隠してから記事に入れます。最後に PR をマージすると Qiita に投稿されます。

  1. ネタ候補 Issue（毎週 / /ideas / /add-idea）
  2. /write で下書き PR と自動レビュー
  3. /revise で修正・感想を反映
  4. ローカルでスクショ撮影・マスク
  5. /publish → マージで投稿

06 / Folder map

どこに、何がある？

日常的に見る場所は drafts/、public/、images/。自動投稿や AI 向けの設定は .github/ にまとまっています。

drafts/

執筆中の Markdown 原稿。ここだけの変更は自動投稿のきっかけになりません。

public/

Qiita CLI の投稿対象となる原稿。配置しただけでは投稿済みとは限りません。

images/

記事や検証で使う画像。verification/ 配下には検証時の画面があります。

.github/

agents/ は役割、skills/ は詳しい手順、prompts/ は定型の依頼文。workflows/ に自動投稿の設定があります。

scripts/

PowerPoint の作成やテンプレート加工を補助する Python スクリプト。

report/

過去の作業報告と、このガイドを置く場所。

package.json
qiita.config.json

Qiita CLI の依存関係とプレビューなどの設定。package-lock.json は依存関係を固定します。

Optional / PowerPoint

スライド用スクリプトは別の道具

  • create_pptx.py：テンプレートを使って比較資料を作成。
  • generate_pptx.py：変換済みテンプレートを使って比較資料を作成。
  • add_layouts_to_template.py：テンプレートにレイアウトを追加。元ファイルを上書きします。
スライドの内容やファイルの場所はコード内に固定されています。現在のフォルダには Template/ が見当たらず、古い出力先を指す設定もあるため、使う前に必要なファイル・依存関係・上書き先を確認してください。Qiita の自動投稿時にこれらが動く設定はありません。

Good to know

設定を見るときの補足

  • 共通ルールと執筆スキルは Qiita 前提。一部のエージェントやプロンプトには、以前の Zenn に関する記述も残っています。
  • 説明上の保存先 verification/ や snippets/ は、今回確認したルートにはまだありません。
  • 公開記事の実例では、Qiita で画像を参照できるよう GitHub の raw URL を使用しています。

共通ルール · 構成変更の作業報告

迷ったら、この3つだけ。

  1. 書いている間は drafts/。
  2. 内容と公開範囲を確認し、public/ へ。
  3. main に push すると、条件に応じて投稿処理が動く。
